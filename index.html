The formula chain, step by step (generic -- applies to every folder)

1
Quantity in, typed by the estimator
A count of cases/coils/equipment items, sourced from a drawing schedule or a scope letter, or an aggregate judgment call when neither cleanly states a total.
2
XLOOKUP converts quantity into material $ and labor hours
Every category (Display Cases, Evaporators, Equipment) has its own small rate table; the formula is always qty x XLOOKUP(type, rate table).
3
Hours classified as ST / OT / DT
Sometimes automatic, sometimes a manual estimator choice (e.g. a "night work" clause pushing everything into Overtime).
4
Hours blended across 5 roles, by a per-project %
Foreman / Startup / Journeyman / Apprentice / Tradesman -- a staffing-policy input.
5
Each role's rate = base wage x burden, with additive OT/DT loading
ST cost-rate = base x (burden+0) OT cost-rate = base x (burden+0.5) DT cost-rate = base x (burden+1) Minneapolis region code "539" is a hardcoded exception: +1/+2 instead of +0.5/+1
6
Cost becomes Sell via reverse-margin
Sell = Cost ÷ (1 - margin%) NOT Cost x (1+margin%)

Naming trap confirmed on HEB 57: BidCalc's own "Markup" column shows a different number than SUMMARY's "Margin %" column for the exact same dollars -- e.g. Margin 25% shows up in BidCalc as Markup 33.3%. Same economics: markup-on-cost = margin/(1-margin). Not a discrepancy, just two tabs describing the same relationship differently -- don't treat a mismatched-looking percentage as an error without checking which convention that tab uses.

7
Tax: category is automatic, rate is always manual
Tax category comes from an XLOOKUP on State + Construction-Type into the TAX TABLE tab. The tax rate is always typed by hand after the estimator manually Googles it -- a HYPERLINK formula literally opens the search, with a note warning to verify multiple results. This is the one universally manual step in an otherwise formula-driven chain, on every folder checked so far.
8
Everything rolls into BidCalc
Labor + Materials + Rentals + Subcontractors + Contingency + Warranty + Tax, each with its own category-specific margin, summed into one Total Bid.

Standard boilerplate present on every workbook

A default Exclusions list -- mostly fixed, but not always identical
The same 13-item list appeared byte-identical on six of the seven folders checked so far: General Contracting, Permits and Fees, Engineering/Drawings, EMS, Seismic work, Local municipality requirements, Roof/floor/wall openings, Trenching/concrete/backfill, Case refurbishing/repair, Case transport/storage/disposal, Plumbing and case condensates, Electrical, Line covers/flashing. Walmart 0344-1005 was the lone exception, adding a 14th item, "Structural/Steel Work" -- plausibly because that job's scope genuinely involves structural work to mount new condenser frames; Trader Joe's #455 and Sam's Club 8250-1010 (both of which also involve real structural/mechanical work) stayed at 13 items regardless. So this list is a default that can be edited per project, but usually isn't even when the scope would justify it -- worth checking the exact wording on every future folder rather than assuming it matches. HEB 383 introduces a second kind of exception: instead of adding a 14th item, its copy is cut short after the 7th item (General Contracting through Roof/floor/wall openings) -- the remaining 6 (Trenching/backfill, Case refurbishing, Case transport, Plumbing/condensates, Electrical, Line covers) are simply absent, not overridden. Some of those (the case-related ones) plausibly don't apply to a case-less ice room; others (Electrical, Line covers) have no obvious reason to be missing. Joe V's #831 repeats the exact same 7-item truncation -- confirming this is a real, recurring template variant rather than a one-off unique to HEB 383, even though Joe V's #831 is a full-scope job where the case-related exclusions would clearly apply.
BidCalc is always authoritative; SUMMARY's own labor breakdown never is
Every workbook checked so far has a "LABOR COST BREAKDOWN (REFERENCE ONLY) -- Do NOT Adjust" block on the SUMMARY tab. It's a sanity-check mirror. BidCalc is the tab that actually produces the number quoted to the customer.
A template-wide formula bug: Contingency Factor's sell price ignores its own margin cell
Confirmed on six separate folders now (HEB Corp #458, Walmart 0344-1005, Trader Joe's #455, Sam's Club 8250-1010, HEB 383, and Joe V's #831), with margin percentages typed into the Contingency Factor's own margin cell repeating mostly at 5% (5%, 3.5%, 5%, 5%, 5%, and 5% again). In every case, the cost is correctly computed off that cell, but the sell value is computed with a hardcoded divisor (cost ÷ 0.8, equivalent to a flat 25% markup every time) instead of referencing the same cell used for cost. Two other rows (Project Management Fee, Performance Bond) carry the identical hardcoded-divisor pattern. This is a defect baked into the template itself, not a one-off data-entry mistake -- it will inflate the sell price on any future folder where Contingency, Project Management Fee, or Performance Bond actually carries a non-default margin.
The HVAC tab's own header block is internally misaligned
Confirmed on six separate folders now (HEB Corp #458, Walmart 0344-1005, Trader Joe's #455, Sam's Club 8250-1010, HEB 383, and Joe V's #831): the HVAC tab's header labels and values are shifted out of alignment relative to each other (e.g. "BID DATE:" displaying the project city, "SCOPE:" displaying "Texas", "DRAWINGS DATE:" displaying the scope text, "REVISIONS #:" displaying a raw date serial number). Harmless every time because the tab itself is entirely unused, but it's a template-level copy-paste artifact, not a project fact -- don't read anything into it if it shows up again.
